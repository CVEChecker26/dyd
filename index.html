    How dyd↻ decides

    Each vulnerability is evaluated separately. Every fact is labelled as declared by you, verified by dyd↻, inferred, or unknown. Checks run in a fixed order and stop at the first one that decides.

    ! Affected according to the available evidence

    The declared version is below the fixed version, the version comes from the PHP that serves the site, and nothing contradicts it. A restart does not change this.

    ✓ Remediation supported by the available evidence

    The declared version is at or above the fixed version, it comes from the PHP that serves the site, you confirmed an update and a restart, and no other runtime is in doubt. This is a statement about these two CVEs only.

    ? Needs further verification

    A detail is missing, unconfirmed, contradictory or outside the verified rules. dyd↻ does not guess.

    Order of the checks

    1. Missing or malformed input stops here and shows errors beside the fields.
    2. Unsupported environments, provider-managed PHP, non-official Docker images and Plesk on Windows need further verification.
    3. Pre-release versions, unsupported branches and package versions in an unexpected format need further verification.
    4. Each CVE is compared with the fixed version for the selected environment, using that environment's own method.
    5. An update that you say was installed, but a version below the fixed one, is a conflict that needs clarification.
    6. A version that is not confirmed as coming from the PHP serving the site needs further verification.
    7. Below the fixed version: affected. At or above it: remediation is supported only if you confirmed the update and a restart and did not say that other PHP runtimes exist; otherwise it needs further verification.

    What dyd↻ never does

    • It never claims or implies that a server was scanned, audited or certified.
    • It never logs in, reads credentials or asks for them.
    • It never infers a PHP version from a CMS, a server header or a domain name.
    • It never treats a failed browser request as proof that a site is vulnerable, fine, or offline.
    • It never judges other CVEs or presents a mitigation as a replacement for updating.
